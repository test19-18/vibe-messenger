# Как вносить изменения

## Базовый процесс

1. Создайте небольшую тематическую ветку.
2. Не добавляйте API-ключи, `.env`, keystore и service-role credentials.
3. Отформатируйте код: `dart format lib test`.
4. Запустите `flutter analyze` и `flutter test`.
5. Для UI-изменений проверьте узкий экран, large text и системную кнопку Back.
6. Опишите изменение схемы Supabase отдельно; миграции ведутся ответственным backend-агентом.

## Архитектурные правила

- UI зависит от Riverpod providers/services, а не обращается к Supabase напрямую.
- JSON/PostgREST преобразуется в моделях через ручные `fromMap/toMap`.
- Репозитории отвечают за таблицы и transport errors; сервисы — за пользовательские операции (reply/edit/delete/read/typing).
- Публичные маршруты ограничены auth-экранами. Новые защищённые маршруты добавляются в `appRouterProvider`.
- Для каждого async-экрана обязательны loading, empty и error состояния.
- Не используйте codegen без отдельного архитектурного решения.

## Стиль

- Названия в коде — английские; пользовательские строки текущего этапа — русские.
- Используйте токены `AppColors`, `AppSpacing`, `AppRadii`, а не случайные цвета/отступы.
- Новые зависимости должны иметь понятную необходимость и быть совместимы с Flutter stable.

## Backend

Не меняйте `supabase/migrations` в рамках Flutter-задач. Ожидаемый контракт документируется в `docs/ARCHITECTURE.md`. Все таблицы должны быть защищены RLS; клиент использует только anon/publishable key и пользовательскую JWT-сессию.
